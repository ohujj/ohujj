**Tech**: Java, Spring Boot, Spring Data JPA, MySQL, Docker, AWS EC2, GitHub Actions, Kakao Route API

#### 담당한 내용

* API 및 DB 설계
* 일정 후보 집계 로직 구현
* 장소 추천 로직 및 Kakao Route API 연동
* Docker, AWS EC2, GitHub Actions 기반 배포·운영 환경 구축

#### Problem Solving

**외부 Route API 병목 개선**

후보별 Route API 호출이 직렬로 실행되어 참여자와 후보 수에 따라 응답시간이 누적되는 병목을 확인했습니다. 호출을 병렬화하되 동시에 실행되는 작업을 최대 2개로 제한해 서버 자원과 외부 API 호출 집중을 제어했습니다.

* 동일 조건 기준 응답시간 **9.63초 → 5.90초**, **38.8% 단축**
* 대기열이 생기는 상황도 고려해, 메모리 여유와 외부 API 호출 집중 사이의 균형을 기준으로 동시 실행 수를 2개로 결정

**추천 후보 수 검증 및 운영값 결정**

후보 수 `K=3`, `K=5`, `K=10`을 13개 출발지 시나리오에서 독립적으로 비교하고, 실제 Route API 응답으로 최종 Top 3와 호출 수를 검증했습니다.

* 비교 가능한 12개 시나리오 모두에서 `K=3`과 `K=10`의 최종 Top 3 구성이 달랐음
* `K=10`이 더 나은 1위 후보를 찾은 4개 사례에서 실제 이동시간 점수가 **1.8% - 15.3% 개선**
* `K=5`는 `K=10` 대비 Route API 호출량을 **50% 수준**으로 유지하면서 후보 누락 가능성을 줄여 MVP 운영값으로 선택

#### Engineering Decisions

* **동시 참여 정합성**: 정원 마지막 1자리에 여러 요청이 동시에 들어오는 상황을 고려해 모임 단위에 비관적 락을 적용했습니다. 락 획득 후 참여 인원 확인부터 저장까지 하나의 트랜잭션으로 처리해 정원 초과를 방지했습니다.
* **회원·게스트 참여 모델 통합**: 회원과 게스트가 같은 일정·출발지·추천 흐름을 사용하도록 하나의 참여자 모델로 통합했습니다. 회원은 계정 정보와 연결하고, 게스트는 별도 비밀번호 인증을 사용해 참여 흐름의 분기를 최소화했습니다.
* **참여 시점의 출발지 보존**: 회원의 현재 주소를 직접 참조하지 않고 참여 시점의 출발지 정보를 별도로 저장했습니다. 이후 회원 정보가 변경되어도 기존 모임의 추천 기준이 바뀌지 않도록 했습니다.
* **마감시간 서버 검증**: 클라이언트 시간이나 화면 상태가 아니라 서버에서 계산한 마감 시각을 기준으로 참여·수정 가능 여부를 검증했습니다. 마감 이후에는 신규 참여와 응답 수정을 차단합니다.
